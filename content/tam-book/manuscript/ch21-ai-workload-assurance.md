# 第 21 章　护航 AI 工作负载

> AI 变革篇第一章，回答主线课题的第一条线：**AI 作为客户的工作负载，TAM 怎么护航它**。客户的 LLM 客服、投研助手、信贷审核 Agent 正在进入核心链路——这些系统的风险形态、成本结构、供给链与传统系统都不同。用旧地图护航新负载，是金融级场景的新风险源。本章给出新地图。

## 21.1 AI 工作负载与传统负载的本质区别

| 维度 | 传统系统 | AI 工作负载（LLM/Agent） |
| --- | --- | --- |
| 故障形态 | 错了是 bug，可复现可定位 | 错了是概率事件，"昨天对今天错" |
| 容量单位 | QPS、CPU、内存 | token 吞吐、上下文长度、GPU 数量与型号 |
| 成本曲线 | 阶梯式（按容量） | 近似线性（按 token/调用量），随业务量放大 |
| 变更含义 | 代码/配置变更 | **模型版本变更 = 系统变更**，且行为不可完全枚举 |
| 回退含义 | 回滚代码版本 | 回滚模型版本 + 验证输出质量回归 |
| SLA 对象 | 可用性、延迟 | 可用性、延迟 + **输出质量水位** |

护航 AI 负载的元原则一句话：**把"模型"当作一种新型的、行为不可完全枚举的基础设施组件来治理**——它要进变更管理、要进容量规划、要进上线闸门、要进重保，但每一处的判据都要为"输出不确定性"做扩展。本章 21.2–21.5 逐域展开。

## 21.2 GPU 容量与排队

GPU 是 AI 时代的新型生产资料，管理要点与传统容量（第 5 章）同源但参数全变：

- **容量模型**：推理容量 ≈ f（并发会话数 × 平均上下文长度 × 生成长度 × 时延要求）。back-of-envelope 示例：峰值 200 并发、平均上下文 4K token、要求首 token 延迟 < 1 秒，按所选模型的单卡吞吐折算 GPU 数量，再乘 1.5–2 倍冗余系数——量级估算能力在 AI 项目评审席上同样是可信度来源；
- **训练与推理的资源争抢**：共用 GPU 池时训练任务会挤占推理容量，评审时必须问清隔离策略（分池、分时、优先级抢占）；
- **排队设计**：推理请求峰值超过容量时的行为——排队、降级（切小模型）、还是拒绝？这是架构决策不是运维细节，要写进设计文档；
- **供给链风险**：GPU 采购周期以季度计、云厂商 GPU 配额有上限且区域性紧张（厂商通告动态见附录 F，以厂商最新通告为准）。容量规划必须包含"拿不到卡怎么办"：多区域、多供应商、模型降级链。

## 21.3 推理成本与 FinOps

AI 负载的成本曲线是近似线性的——业务量越成功，成本越高，这在传统系统里不常见（传统系统靠规模摊薄）。**推理成本失控是 AI 项目被叫停的第一大非技术原因**。

TAM 要推动的四件事：

1. **单位经济学先算清**：每千次对话成本、每笔业务（一次信贷审核、一份投研报告）的推理成本，换算到业务口径（第 6 章翻译公式：成本也要翻译）；
2. **成本基线与异常检测**：token 消耗量进监控大盘，异常突增（提示词注入攻击、循环调用、程序 bug 的重试风暴）按事件处理；
3. **降本杠杆组合**：大小模型分层路由（简单问题小模型）、语义缓存、量化部署、提示词瘦身、离线批处理错峰——按收益排序逐个评估；
4. **成本进治理节奏**：月度服务报告增加推理成本一栏，QBR 呈现单位成本趋势（第 8、15 章）。

自建 GPU 与按 token 计费的 API 之间存在盈亏平衡点，随业务量变化——这个测算至少每半年重做一次，结论可能翻转。

## 21.4 模型评估与上线闸门

**模型版本变更 = 系统变更**，必须进变更治理（第 8 章）：模型升级要走评审、要有回退、要避开业务峰值窗口。AI 项目的上线闸门在第 10 章框架上扩展四个判据：

1. **离线评估过线**：在黄金评估集上的准确率/合格率 ≥ 约定红线，且**不劣于当前生产版本**（回归测试）——评估集要客户业务侧参与构建，否则评的是题库不是业务；
2. **幻觉与拒答策略明确**：不知道时拒答还是猜测？错误答案 vs 拒答的业务代价不同（信贷场景错误通过 ≫ 拒答），策略要业务侧签字；
3. **降级方案实测**：模型服务不可用时回退到什么——旧模型、规则引擎、人工通道？回退通道要实测，标准同第 18 章（没实测等于没有）；
4. **人工接管率预算**：AI 处理不了转人工的比例预估与人力校核——Agent 系统上线最常见的翻车不是模型不行，是人工坐席被转介流量打爆。

**SLA 的写法也要变**：传统"可用性 99.9%"对 AI 负载不够，要加输出质量维度——例如"抽检合格率 ≥ 95%""人工接管率 ≤ 20%""高危错误（资损/合规类）= 0"。质量水位的测量方式（抽检频率、样本量、判定人）写进协议，否则又是口径争议（第 8 章的教训）。

## 21.5 RAG、微调与 Agent 的架构评审要点

在第 5 章评审六维之上，AI 架构的专项提问清单（并入模板 03 的 AI 专项）：

**RAG 链路**：

- 知识库文档质量与更新机制（垃圾进垃圾出，过期知识 = 可信的错误答案）；
- 召回质量怎么测、多久测一次；
- **权限隔离**：不同密级的文档是否分区索引？用户提问会不会召回他无权看的文档？（数据出域与越权是金融 RAG 的头号评审项，接第 9、24 章）；
- 知识库变更是否走变更管理。

**微调**：

- 训练数据来源与合规（含不含个人信息、有没有授权）；
- 训练/生产隔离与模型版本管理（哪个微调版本在生产、如何回滚）；
- 基座模型升级策略：基座 EOL 了微调产物怎么办。

**Agent 系统**（风险最高，评审最严）：

- 工具调用权限最小化：Agent 能执行什么操作？写操作是否有人工确认（human-in-the-loop）？
- 循环失控防护：最大步数、最大 token 预算、超时熔断；
- 全链路审计日志：谁触发、调了什么工具、依据什么输出做了动作——**没有审计日志的 Agent 不得进金融生产环境**；
- 提示词注入面：Agent 读取外部内容（网页、邮件、文档）时，注入防护与不可信内容隔离。

## 21.6 AI 项目的重保增量项

AI 负载进重保（第 18 章框架不变），体检与预案增加六项：

- [ ] 模型版本冻结（窗口期禁止模型升级）
- [ ] 评估集回归测试通过记录
- [ ] GPU 容量与配额锁定确认
- [ ] 推理降级链实测（主模型 → 备模型 → 人工）
- [ ] token 消耗异常告警阈值设定
- [ ] 第三方模型 API 的 SLA 与限流确认

## 21.7 自检清单

- [ ] 负责客户的 AI 负载清单在手：模型、版本、提供方、所在链路
- [ ] 每个 AI 负载的容量模型（token 口径）与供给风险预案明确
- [ ] 推理单位成本算得清、在监控、进 QBR
- [ ] 模型升级走变更治理，评估集回归是硬性闸门项
- [ ] 每个 AI 负载有实测过的降级/回退通道
- [ ] RAG 权限隔离与 Agent 审计日志通过评审
- [ ] AI 负载的 SLA 含输出质量维度且测量口径书面化
- [ ] AI 重保增量六项纳入重保 Checklist（模板 05）

---

**本章要点回顾**

1. 元原则：把模型当作行为不可完全枚举的新型基础设施组件来治理，一切传统纪律照旧，判据为输出不确定性做扩展。
2. GPU 容量：新容量模型 + 训练推理隔离 + 排队设计 + "拿不到卡怎么办"的供给预案。
3. 推理成本近似线性增长，是 AI 项目被叫停的第一大非技术原因：单位经济学、成本基线、降本杠杆、进治理节奏。
4. 上线闸门加四判据：评估过线（不劣于现版本）、幻觉/拒答策略签字、降级实测、人工接管率预算；SLA 必须含输出质量维度。
5. RAG 头号评审项是权限隔离，Agent 的硬门槛是审计日志 + 人在回路；AI 重保在第 18 章上加六个增量项。
