# 附录 E　开源贡献指南：如何提交勘误、案例与模板

> 本书是开源技术图书：读者即共建者。你的勘误让口径不失真，你的（脱敏）案例让打法有血肉，你的模板让工具箱更好用。本指南约定三类贡献的提交方式与质量门槛。**一切贡献以不破坏全书"唯一事实源"体系为前提**——这是评审的第一道关。

## E.1 贡献方式总览

| 类型 | 适合贡献什么 | 入口 | 评审要点 |
| --- | --- | --- | --- |
| 勘误 | 事实错误、口径漂移、交叉引用失效、错别字 | Issue（勘误模板） | 是否给出依据与建议改法 |
| 案例 | 行业实战场景（金融/政企/互联网……） | Issue（案例模板）→ 讨论 → PR | 脱敏是否彻底、结构是否完整 |
| 模板 | 新工具模板、既有模板改进 | Issue（模板提案）→ 讨论 → PR | 体例合规、与既有编号不冲突 |

通用流程：**先 Issue 后 PR**——直接 PR 大改动大概率被要求返工，先在 Issue 里对齐口径再动笔。

## E.2 勘误提交

好的勘误四要素齐全，缺一退回补充：

1. **位置**：文件路径 + 节号（如 `manuscript/ch08-service-governance.md` 8.3 节）；
2. **原文**：引用出错的那段话；
3. **建议改法**：给出替换文字，不只是"这里不对"；
4. **依据**：数据/行情/监管条文类勘误必须附来源链接与时点（本书约定：时效性内容一律标注来源与时点，见各附录头部声明）。

以下情形请按勘误处理，不要直接改：指标口径（唯一事实源在第 26 章，别处只引用）、术语（唯一事实源在附录 A，改动须同步术语表）、流程编号（P1–P12 全书通用，见附录 B）。

## E.3 案例征集

案例是本书最缺的原料，也是风险最高的贡献类型——**脱敏是硬门槛，不是建议**。

### 脱敏三条规定（AGENTS.md 写作约定）

1. 不使用真实客户名、真实人名；系统/厂商名按需要泛化（"某国有大行"→ 建议进一步虚构为"A 银行"式代号，与第 18 章样章一致）；
2. 去除可反推身份的细节组合（独特架构 + 特定时间 + 特定故障的组合本身就是指纹）；数字可微调但**保真结构**（比例关系、量级、因果链不许美化）；
3. 提交即声明：案例已获必要授权，且不包含任何保密信息。

### 案例结构（与第 20 章案例集体例一致）

```
背景（客户类型与业务场景）→ 冲突（发生了什么）→ TAM 动作（具体做了什么、依据什么）→ 结果（可核验的结局）→ 复盘（教训是什么）
```

评审会追问的两个问题：这个案例**支撑书中哪个论点**？删掉它哪个论点会站不住？答不上来的案例不收录——案例不是故事会。

## E.4 模板共建

### 新模板提案

Issue 中写明四件事，通过后再动笔：

1. **使用场景**：谁在什么时候用这张表；
2. **配套锚点**：对应哪一章/哪个附录/哪个流程号（无锚点的模板不收——工具箱不是杂货铺）；
3. **编号**：`templates/<编号>-<英文 slug>.md`，编号与目录工具箱清单一致；新编号**先查占用**——既有前缀包括 P/L/M/C/OT/RT/CH/PL/PR/TK/SM/D/G/H/T 各系（HANDOFF 与附录 A.3 有索引），新系列请声明避让逻辑；
4. **体例**：沿用既有模板约定——头部三行（用途/用法/时点）、□ 勾选项、阈值注明"建议值按业务校准"、末尾版本记录表。

### 既有模板改进

- 小改（措辞、错别字、锚点数值建议）直接 PR，说明理由；
- 结构改动先在 Issue 讨论：模板被章节与附录交叉引用，动结构前要 grep 引用方并同步；
- 任何改动追加版本记录行，**不改写历史版本行**。

## E.5 全书维护纪律（贡献者必读）

改动以下内容时，必须同步其"唯一事实源"，否则评审不予通过：

| 改什么 | 同步哪里 |
| --- | --- |
| 章节结构（增删章/改章名） | 目录 `manuscript/00-outline.md`（目录是唯一事实源，改目录先于改正文） |
| 术语（新增/改名/改译） | 附录 A 术语表 |
| 指标口径 | 第 26 章（其他位置只许引用，不许重定义） |
| 流程编号 P1–P12 | 附录 B |
| 文件命名 | 章节 `ch<章号>-<slug>.md`、附录 `appx-<字母>-<slug>.md`、模板 `templates/<编号>-<slug>.md` |
| 章节正文 | 章末保留/更新"本章要点回顾"；涉及其他章的交叉引用随改动核对 |

协作工程细节（并发期开工登记、踩坑记录）见仓库 `HANDOFF.md` 与 `AGENTS.md`，参与高频共建前请通读。

## E.6 许可与署名

- 内容许可以仓库根目录 LICENSE 文件为准；提交即视为同意按该许可发布；
- 贡献者署名：在对应文件版本记录或致谢节留名（ID/昵称即可），案例类贡献默认匿名化处理署名（保护来源）；
- 重要争议（口径分歧、收录与否）由维护者在 Issue 内公开裁定并记录理由——裁定结论同步进 HANDOFF，避免同一争论反复发生。

## E.7 什么样的贡献会被拒

- 未脱敏或脱敏不彻底的案例（一票否决，不返工）；
- 无出处与时点的时效性数据；
- 绕过唯一事实源的"就地修正"（改指标口径不动第 26 章、改术语不动附录 A）；
- 无配套锚点的新模板、与既有编号冲突的新编号；
- 纯观点输出（"我觉得应该更重视 X"）——欢迎改写为可执行的条目再来。

---

**本章要点回顾**

1. 三类贡献：勘误（四要素）、案例（脱敏三条规定 + 五段结构）、模板（四件事提案 + 体例约定）；统一流程先 Issue 后 PR。
2. 维护纪律的本质是守住唯一事实源体系：目录、术语表、第 26 章、附录 B、命名约定——改动必同步。
3. 拒绝清单即质量门槛：脱敏一票否决；无出处不收；绕过事实源不收；无锚点不收。
